# Converting a Utopia library from PHP to Rust

The standard every Rust Utopia crate is held to. It turns the goals of the migration ([rfc/rust.md](../rfc/rust.md)) into rules for one library at a time, and defines what "converted" means so it can be measured instead of claimed.

The tool that measures it is the compatibility framework in [`tests/compat`](../tests/compat/README.md). Read both before converting or reviewing a library.

## 1. Scope

A Utopia library is a PHP package in `packages/<name>` (or a `utopia-php/<name>` package still in `vendor/`). Its Rust equivalent is the crate `crates/utopia/<name>`, published in the workspace as `utopia-<name>`.

A library is converted **when a migrated service first needs it, and then in full**. A crate never ships with only the parts one service uses: the first service to need a library pays for its complete conversion. Libraries no migrated service needs yet stay PHP-only.

`utopia-php/query` is converted with `database`, as the crate `utopia-query`, because the database adapters build their SQL with it.

## 2. What "100% converted" means

A library is converted when all of these hold, and not before. `bin/compat check <lib>` verifies the first five.

1. **API coverage is 100%.** Every public method and function of the PHP library (the inventory `bin/compat coverage <lib>` takes by reflection) is covered by a compatibility operation, or waived in `tests/compat/<lib>/spec.json` with a reason the waiver rules in §6 allow.
2. **Every backend exists.** If the PHP library has several adapters (cache: Redis, Redis Cluster, Memcached, Filesystem, Memory, ...; database: PostgreSQL, MariaDB, MySQL, SQLite, MongoDB, ...), the crate has all of them. Optional backends sit behind cargo features; none is missing.
3. **The PHP tests are ported.** Every test class in `packages/<name>/tests` has a case file in `tests/compat/<lib>/cases/` (its `source` names the PHP test) covering the same assertions. Behaviour that needs a service (Redis, a database) is ported too, against the dev stack.
4. **Differential runs are clean.** `bin/compat run <lib>` (every case on PHP and Rust, outputs and side effects compared) and `bin/compat fuzz <lib>` (generated inputs, at least the iterations the spec sets) report zero differences.
5. **Shared formats interoperate.** Anything both runtimes read or write (cache entries, queue messages, locks, password hashes, encrypted values, rows, keys) has interop cases where one runtime writes and the other reads, in both directions.
6. **The workspace stays green.** `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings` and `cargo test --workspace` pass, every consumer in `crates/appwrite/*` is updated, and the PHP E2E suites of migrated services still pass against Rust.
7. **Hot paths are benchmarked.** Operations on a request path have a benchmark comparing PHP and Rust, and Rust must be faster and allocate less.

The status of every library is in [`tests/compat/STATUS.md`](../tests/compat/STATUS.md), generated by `bin/compat status`.

## 3. Behaviour: identical where observable

Rust must behave exactly like PHP wherever a caller, another service or a stored byte can tell the difference. Inside, it should not resemble PHP at all (§4).

- **Results.** Same values and same types: an `int` stays an integer and a `float` stays a float (`1` is not `1.0`), `null` stays `null`, list order and map key order match.
- **Errors.** The same failure raises the error that corresponds to the same PHP exception class, with the same message, byte for byte. Each crate's error enum has one variant per PHP exception class (§4), so the mapping is mechanical.
- **Side effects.** The same operation leaves the same state behind: Redis keys, types, values and TTLs; SQL tables, columns, indexes and rows; queue messages; files. The framework snapshots and compares them.
- **Wire and storage formats.** Formats shared between runtimes are contracts: Rust reads what PHP writes and writes what PHP reads. Where PHP uses a PHP-only encoding (`serialize`, igbinary), Rust implements that encoding rather than introducing its own, unless both runtimes switch formats together in one change.
- **Text.** PHP string functions are byte based (`strlen`, `substr`, `strtolower` are ASCII only) and `mb_*` functions are character based. Use the same unit the PHP code uses. Byte-level behaviour on invalid UTF-8 must match too.
- **Numbers.** PHP integers are 64-bit and overflow into floats. Floats print with `precision = 14` in strings (`(string) 0.1 + 0.2` is `"0.3"`, `1e25` is `"1.0E+25"`) and with `serialize_precision = -1` in `json_encode` (`0.30000000000000004`, `1.0e+25`). Use `php_std::number` instead of Rust's `Display` for anything PHP would print.
- **PHP functions.** When behaviour comes from the engine (type juggling, `==`, `is_numeric`, `filter_var`, `parse_url`, `json_encode`/`json_decode`, `preg_*`, `strtotime`, `number_format`, `mb_*`), use or add its reimplementation in [`crates/support/php-std`](support/php-std), where each function is fuzzed against the real one (`bin/compat fuzz php-std`). Never approximate one inside a library.
- **Regular expressions.** A PHP pattern keeps PCRE semantics: without `/u` it matches bytes (use `regex::bytes` with `(?-u)`), without `/D` a `$` also matches before a final newline, and `\d`, `\w`, `\s` are ASCII unless `/u` is set.
- **Quirks.** Behaviour that looks like a bug is kept, recorded under `quirks` in `spec.json` with a pinned case, and fixed in PHP and Rust together later (rfc §4). Never "fix" it silently in Rust.

## 4. Design: native Rust, same boundaries

From the migration brief. These are review criteria, not suggestions.

- **Do not mirror PHP.** Keep the library's responsibilities, boundaries and separation of concerns; do not copy its class hierarchy, getters and setters, magic methods, arrays-as-structs or exceptions-as-control-flow. Use enums, traits, generics, newtypes, `Result` and ownership.
- **One crate per library, strict boundaries.** `crates/utopia/<name>` holds one library. A Utopia crate never depends on an `appwrite-*` crate. Dependencies between Utopia crates follow the PHP packages' `require` graph and never form a cycle. Do not fold library code into `crates/appwrite/*`, or Appwrite code into a library.
- **Extensible without forks.** Anything PHP lets a consumer replace or add (adapters, validators, hooks, resources, providers) is a public trait or a registration point in Rust, so Appwrite Cloud can extend CE crates from outside. Do not close an extension point PHP leaves open with a sealed enum.
- **Performance first.** No unnecessary allocations, copies, `dyn` dispatch, serialization, locks or round trips. Borrow instead of cloning; prefer static dispatch on hot paths; batch and pipeline I/O; keep one statement per write where PHP's semantics allow it.
- **Async I/O.** Network and disk I/O is async on tokio. Nothing blocks a runtime thread: CPU-heavy work (hashing, compression, image work) runs on the blocking pool.
- **Errors.** One `thiserror` error enum per crate. Variants map one to one onto PHP exception classes, carrying the same message, and `Error::php_class()` returns the PHP class name (compat adapters report it).
- **Backends behind features.** Each optional backend is a cargo feature (`postgres`, `mysql`, `sqlite`, `mongodb`, `memcached`, ...) so binaries only link what they use. CI builds with `--all-features`.
- **Dependencies.** Add third-party crates to `[workspace.dependencies]` with a reason in the PR. Prefer maintained, pure-Rust crates; avoid C dependencies unless there is no adequate alternative.
- **Naming.** Rust naming (`get_description()` becomes `description()`, `isValid` becomes `is_valid`). The crate docs carry a table mapping each PHP class to its Rust item, so a reader of one runtime can find the other.
- **No `unsafe`** unless a benchmark proves it necessary, with a `// SAFETY:` comment.
- **Configuration.** Environment variables keep their PHP names (`_APP_*`), read through `utopia-system`.

## 5. Process for one library

1. **Inventory.** `bin/compat coverage <lib>` lists the PHP API. Read the PHP source and tests end to end.
2. **Spec.** Write `tests/compat/<lib>/spec.json`: the operations (a neutral vocabulary both runtimes implement), which PHP symbols each covers, fuzz generators, waivers and quirks.
3. **PHP adapter.** `tests/compat/<lib>/Adapter.php` maps each operation onto the PHP library. It is thin glue: no logic and no normalisation beyond turning values into JSON.
4. **Cases.** Port every PHP test class to `tests/compat/<lib>/cases/<Test>.json`. Add edge cases the PHP tests miss, and interop cases for shared formats.
5. **Rust.** Implement the crate, then `crates/tools/compat/src/libs/<lib>.rs`, the Rust adapter, which is equally thin. Appwrite-specific behaviour found in the old Rust crate (Appwrite env vars, fail-open policies, Appwrite error codes) moves to `crates/appwrite/core`: the reference is `appwrite_core::locking`, the port of `src/Appwrite/Locking/Lock.php` that used to live in `utopia-lock`.
6. **Converge.** Run `bin/compat run <lib>`, `bin/compat fuzz <lib>` and `bin/compat coverage <lib>` until they are clean. Every difference is a Rust bug, a PHP quirk to record, or a missing case: never a reason to loosen a comparison.
7. **Record.** `bin/compat record <lib>` stores PHP's results as `expect` in the case files, so `cargo test -p compat` replays them without PHP.
8. **Integrate.** Update consumers in `crates/appwrite/*`, run the workspace checks and the E2E suites of migrated services, add benchmarks, and regenerate `tests/compat/STATUS.md`.
9. **Sync.** `bin/compat sync <lib>` records the PHP commit the crate now matches (`php-sync` in its `Cargo.toml`). It refuses unless the library's cases all match.

### Keeping up with PHP

The team keeps changing the PHP libraries while they are ported. `apps/crates` shows, for every crate, the PHP commits to `packages/<lib>/src` since its `php-sync` point, and what is on `origin/main` but not merged yet. A crate with commits to catch up on is not complete until they are ported: port each change (with its cases, which `bin/compat record` refreshes), then run `bin/compat sync <lib>` again. `bin/compat ci` catches behaviour PHP changed under an existing case; the sync view catches new behaviour no case covers yet.

## 6. Waivers

A waiver excludes a PHP symbol from coverage. It is allowed only when the symbol has no behaviour a Rust caller could need. Every waiver is reviewed.

- **PHP runtime plumbing** with no Rust counterpart: Swoole or FPM server adapters, PSR interfaces, PHPStan extensions, `__destruct`, `__clone`, serialization hooks of PHP objects. The *behaviour* behind them (serving HTTP, pooling) is still converted.
- **Accessors subsumed by Rust types**: a getter or setter whose effect is fully covered by construction or by another operation's cases (`setLength` when `Text::new` and its cases cover length).
- **Deprecated aliases** that only forward to a covered symbol.

A **deviation** is narrower than a waiver: the symbol is covered, but an input PHP accepts cannot be expressed in Rust because a type makes it unrepresentable (an enum instead of an `int` flag), and PHP's only behaviour for it is an error or nonsense. Record each under `deviations` in `spec.json` with the PHP behaviour and the reason; reviewers check every one.

Not allowed: "unused by Appwrite", "hard to port", "rarely used", or anything with observable behaviour.

## 7. Review checklist

- [ ] `bin/compat check <lib>` passes: coverage 100%, run and fuzz clean, every PHP test class ported.
- [ ] Every PHP backend exists, behind a feature where optional.
- [ ] Interop cases for every shared format, in both directions.
- [ ] Each waiver fits §6; each quirk has a pinned case.
- [ ] The design follows §4: no PHP-shaped APIs, extension points kept as traits, no needless allocation or dispatch.
- [ ] Workspace checks pass; consumers are updated; migrated services' E2E suites pass against Rust.
- [ ] Hot paths are benchmarked against PHP.
- [ ] The crate docs map PHP classes to Rust items.
